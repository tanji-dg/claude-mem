# Self-Hosting on Cloudflare Workers

`workers/cmem-server` is the claude-mem **server runtime** packaged as one
Cloudflare Worker. It serves the same `/v1` API as the
[Postgres-backed server](/hosted-server), so the server-mode hooks and MCP
clients connect to it unchanged. Memory lives in **D1**, observations are
generated by your chosen LLM provider, and the Worker needs no servers of your
own.

<Note>
The Worker uses only **Workers, D1 and Cron Triggers**, which are all available
on the Free plan. It does not use Queues, KV, Vectorize or Durable Objects.
</Note>

## Free plan fit

| Resource | Free plan limit | Usage |
|---|---|---|
| Workers requests | 100,000 / day | One per hook event, plus 1,440 cron runs a day |
| Workers CPU | 10 ms / invocation | Waiting on the LLM is I/O and does not count as CPU time |
| D1 rows read | 5,000,000 / day | Every hot query is served by an index |
| D1 rows written | 100,000 / day | About 1,000 observations a day uses fewer than 10,000 |
| D1 queries | 50 / invocation | Writes are grouped with `batch()` |

<Warning>
Limits change. Check the current values at
[Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and
[D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
</Warning>

## How it works

- **Storage:** D1 (SQLite). Full-text search uses an FTS5 table ranked with `bm25()`.
- **Generation:** ingesting an event writes a job row to the
  `observation_generation_jobs` outbox table and generates the observation right
  away with `ctx.waitUntil`. A **Cron Trigger that runs every minute** retries
  queued, failed-for-retry and stale jobs.
- **Providers:** `claude` (default), `gemini` or `openrouter`, chosen with the
  `CLAUDE_MEM_SERVER_PROVIDER` var in `wrangler.jsonc`.
- **Auth:** API keys (`Authorization: Bearer` or `X-Api-Key`). The server
  stores only their SHA-256 hash.

## Deploy

You need a full checkout of the repo, because the build bundles modules from the
repo-root `src/` and `plugin/modes/`. Run these steps from `workers/cmem-server/`:

<Steps>
  <Step title="Install and log in">
    ```bash
    bun install
    bunx wrangler login
    ```
  </Step>
  <Step title="Create the D1 database">
    ```bash
    bunx wrangler d1 create cmem-server
    ```
    Paste the printed `database_id` into `wrangler.jsonc` under
    `d1_databases[0].database_id`.
  </Step>
  <Step title="Apply migrations">
    ```bash
    bunx wrangler d1 migrations apply cmem-server --remote
    ```
  </Step>
  <Step title="Set secrets">
    ```bash
    bunx wrangler secret put CMEM_ADMIN_TOKEN
    bunx wrangler secret put ANTHROPIC_API_KEY   # or GEMINI_API_KEY / OPENROUTER_API_KEY
    ```
    You only need the key for the provider that `CLAUDE_MEM_SERVER_PROVIDER`
    selects. You can also set `CLAUDE_MEM_SERVER_MODEL`,
    `CLAUDE_MEM_SERVER_MAX_OUTPUT_TOKENS` and `CLAUDE_MEM_MODE` under `vars`.
  </Step>
  <Step title="Deploy">
    ```bash
    bunx wrangler deploy
    ```
  </Step>
  <Step title="Bootstrap an API key">
    ```bash
    curl -sS -X POST "https://cmem-server.<subdomain>.workers.dev/v1/admin/bootstrap" \
      -H "Authorization: Bearer $CMEM_ADMIN_TOKEN" \
      -H "Content-Type: application/json" -d '{}'
    ```
    The response is `{ teamId, projectId, apiKey, scopes }`. The raw `apiKey` is
    shown **only once**.
  </Step>
</Steps>

## Connect claude-mem

Add these keys to `~/.claude-mem/settings.json`:

```json
{
  "CLAUDE_MEM_RUNTIME": "server",
  "CLAUDE_MEM_SERVER_URL": "https://cmem-server.<subdomain>.workers.dev",
  "CLAUDE_MEM_SERVER_API_KEY": "cmem_…",
  "CLAUDE_MEM_SERVER_PROJECT_ID": "<projectId>"
}
```

SessionStart then injects context from `GET /v1/context/inject` on the Worker.
For MCP recall, use the `/v1/mcp` path:

```bash
claude mcp add --transport http claude-mem \
  https://cmem-server.<subdomain>.workers.dev/v1/mcp \
  --header "Authorization: Bearer cmem_…"
```

<Warning>
`claude-mem install --runtime server` prints `<url>/mcp` as the MCP target. The
correct path is `<url>/v1/mcp`.
</Warning>

## Local development

```bash
cp .dev.vars.example .dev.vars
bunx wrangler d1 migrations apply cmem-server --local
bunx wrangler dev
```

## Limitations

- Search is FTS5 keyword search (terms ANDed). There is no vector search.
- `/v1/events/batch` accepts at most 20 events.
- `platformSource` is accepted by `/v1/context/inject` but not filtered on.
- The local worker is still used for the viewer UI.

## Security

- Keep `CMEM_ADMIN_TOKEN` secret. Anyone who has it can mint API keys. After
  bootstrapping, you can delete it with `bunx wrangler secret delete CMEM_ADMIN_TOKEN`.
  The bootstrap route then returns `404`.
- Cloudflare Access can front the Worker, but the hooks cannot perform an
  interactive Access login and do not send service-token headers. Enabling
  Access therefore breaks the hooks.

See `workers/cmem-server/README.md` for the full route list and more details.
